# QIE Studio

**Two projects in one repository.**

1. **An application.** QIE Studio is a self-hosted, Docker-deployable image **generation &
   editing** studio built around the [Qwen-Image](https://github.com/QwenLM/Qwen-Image)
   model family — `Qwen-Image-Edit-2511` for instruction-based, multi-image editing and
   `Qwen-Image` for text-to-image generation — wrapped in a modern web UI with LoRA
   management, reusable prompt and image libraries, guided resolution presets, and
   VRAM-aware model selection.

2. **A working demonstration of an autonomous development process.** Almost none of the
   application code in this repository is written by a human. Instead, a human author
   specified *what to build* in exhaustive detail and *granted an AI agent the authority to
   decide how to build it*, then set it loose to implement, test, and document the whole
   thing unattended. This repository is the experiment's substrate: you can read it both as
   a piece of software and as a record of how that software came to exist.

---

## The experiment

The interesting question isn't "can an AI write code?" — it's "what does it take to hand an
AI a real, non-trivial product and have it deliver, on its own, with judgment?" QIE Studio
is structured to answer that. The arrangement is a deliberate split of responsibilities:

- **The human provides a contract, not a transcript.** Rather than dictating code, the
  author wrote a thorough specification describing the product's behavior, the user
  workflows, the data model, the API surface, the deployment story, and — importantly — the
  specific libraries and frameworks the implementation must use (Python 3.13, FastAPI,
  PostgreSQL, PyTorch + diffusers, a React/Tailwind/shadcn front end, and so on). The spec
  is opinionated about the *what* and the *with-what*.

- **The agent owns the decisions the spec doesn't make.** No specification is complete. The
  agent is explicitly authorized to resolve every gap, ambiguity, and unforeseen
  trade-off on its own — choosing approaches, researching options, and proceeding without
  waiting for human input. The one obligation is **disclosure**: each original decision is
  recorded — the context, the alternatives weighed, the research consulted, the choice
  made, and the outcome.

- **The work is unattended and accountable.** Once started, the build runs without human
  observation or course-correction. To make that safe and auditable, the agent keeps a
  timestamped, commit-stamped progress diary designed to be *resumable* — so that after a
  crash, power loss, or interruption, the process can pick up exactly where it left off.

In other words: the human defines the destination and the vehicle; the AI does the driving,
keeps a logbook, and explains every turn it chose to take.

## What's in the repository at the start

Before the autonomous build begins, this repository contains **only specification and
process documents — no application code.** The application is generated by the agent against
these documents. The starting files are:

| File | Role |
|------|------|
| **`DESIGN.md`** | The authoritative product specification. The full picture: the two run modes (Generate / Edit), the four reusable building blocks (images, prompts, LoRAs, resolution presets), the model/precision advisor, the data model, the REST/WebSocket API surface, containerization, the prompt-enhancement design, and the build order. This is the contract the agent must satisfy. |
| **`CLAUDE.md`** | Guidance loaded by [Claude Code](https://claude.com/claude-code) for every session — the locked technology stack, the cross-cutting architecture, and the project-specific constraints that are easy to get wrong (so the agent stays consistent across a long, multi-step build). |
| **`RUN.md`** | The autonomous build runbook. Defines how the unattended run operates: the build environment it can assume, the git/branch workflow, the testing strategy, the commit/push cadence, the progress-diary requirements, and the definition of "done." |
| **`README.md`** | This file. |

As the build proceeds, the agent will add the application itself (backend, frontend, Docker
assets, tests) plus a **`PROGRESS_DIARY.md`** — the running, resumable logbook of the build,
including the disclosed decision records described above.

## How to read this repository

- **If you want the product:** start with `DESIGN.md` for the full specification, then read
  the generated source once the build has run.
- **If you want the experiment:** start with `RUN.md` to understand the rules of the
  autonomous run, then follow `PROGRESS_DIARY.md` chronologically to watch the application
  take shape and to see every judgment call the agent made — and why. (Note: the diary is
  only present in branches - look for a branch with a datestamp and switch to that. We do not
  update the main branch. It's a starting point that we can use for reproducibility.

## The application, in brief

QIE Studio (as specified) lets a user:

- Switch between **Generate** (text-to-image) and **Edit** (multi-image, instruction-based)
  modes that share one workflow.
- Maintain a **library** of reusable images (uploads *and* generated outputs can be
  promoted to it) and a library of **named prompts** — prompts that can pin specific images
  and define open "slots" the user fills at run time (e.g. a fixed room photo plus uploaded
  furniture to stage in it).
- Install and stack **LoRAs** from local upload, Hugging Face, CivitAI, or a direct URL.
- Pick output sizes from guided **resolution presets**, and choose model precision
  (bf16 / fp8 / int4) with the help of a **VRAM-aware advisor** that reads the available
  hardware.
- Watch generations resolve via **live latent previews**, run **batches/sweeps**, and keep
  a fully reproducible **history** of every job.

It targets NVIDIA/CUDA, AMD/ROCm, and Apple Silicon, ships single-user and local, and is
architected to stay open to multi-user and cloud deployment later.
